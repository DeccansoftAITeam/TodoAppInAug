# Technical Requirements Document

## 1. Architecture Overview

The Version 1 Todo application is implemented as a single-repository monorepo with a React frontend and a Python FastAPI backend. The backend is structured in three layers: routers, services, and a repository layer. This separation is enforced by architecture: the router handles HTTP concerns only, the service contains business rules, and the repository is the only component that touches storage. In Version 1, storage is an in-memory Python list inside the repository. There is no authentication, no database, and no category field.

The application is designed for a single user and does not include multi-user access, login, or persistent storage beyond the current process lifetime. The frontend uses functional React components and local state with useState. The backend exposes a REST API with JSON request and response bodies. All data shaping, validation, and API serialization use Python 3.12, FastAPI, and Pydantic models.

Traceability: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8, FR-9, FR-10.

## 3. Data Model

### 3.1 Todo entity

| Field name | Type | Required | Description | Traceability |
| --- | --- | --- | --- | --- |
| Id | string | Yes | Unique identifier for each todo. Generated by the backend and used to reference a specific item. | FR-1, FR-9 |
| Title | string | Yes | Short user-visible task name. Must not be empty or whitespace-only. | FR-1, FR-2, FR-6 |
| Description | string | No | Optional detail for the task. May be empty or null, but must be stored as a string or empty value if not provided. | FR-1, FR-2, FR-6 |
| DateCreated | datetime | Yes | Timestamp recorded automatically when the todo is created; not editable by the user. | FR-1, FR-3 |
| IsCompleted | boolean | Yes | Completion status. Default is false on creation and may be toggled by the user. | FR-1, FR-4, FR-7 |

### 3.2 Validation rules

- `Title` is required for both creation and update.
- Empty or whitespace-only `Title` values are rejected.
- `DateCreated` is set server-side during creation and is not accepted from the client as an editable field.
- `IsCompleted` defaults to `false` when creating a todo.
- The system guarantees a unique `Id` for each entry in the current application lifetime.

Traceability: FR-1, FR-2, FR-3, FR-4, FR-6, FR-7, FR-9.

## 4. API Endpoints

All API routes use JSON request and response bodies. All responses are returned in JSON unless an HTTP status code explicitly indicates no content. The backend is single-user with no authentication or authorization.

### 4.1 Endpoint definitions

| Method | Path | Request body | Response body | Status codes | Traceability |
| --- | --- | --- | --- | --- | --- |
| GET | /api/todos | None | Array of Todo objects | 200 OK | FR-5 |
| POST | /api/todos | `{ "title": "string", "description": "string" }` | Todo object | 201 Created, 400 Bad Request | FR-1, FR-2, FR-4, FR-9 |
| PUT | /api/todos/{id} | `{ "title": "string", "description": "string" }` | Todo object | 200 OK, 400 Bad Request, 404 Not Found | FR-6, FR-9 |
| PATCH | /api/todos/{id}/status | `{ "is_completed": true/false }` | Todo object | 200 OK, 400 Bad Request, 404 Not Found | FR-7, FR-9 |
| DELETE | /api/todos/{id} | None | No content or success message | 204 No Content, 404 Not Found | FR-8 |

### 4.2 Request and response contract

#### Todo output model

```json
{
  "id": "string",
  "title": "string",
  "description": "string",
  "date_created": "2026-08-19T12:00:00Z",
  "is_completed": false
}
```

#### Create request model

```json
{
  "title": "Buy groceries",
  "description": "Milk, eggs, and bread"
}
```

#### Update request model

```json
{
  "title": "Buy groceries for the week",
  "description": "Milk, eggs, bread, and fruit"
}
```

#### Status update request model

```json
{
  "is_completed": true
}
```

### 4.3 Error handling requirements

- Invalid `Title` values are rejected with `400 Bad Request`.
- Requests for a non-existent todo ID are rejected with `404 Not Found`.
- The API returns consistent JSON error payloads for validation and not-found scenarios.
- The client is responsible for rendering user feedback based on these API errors.

Traceability: FR-2, FR-5, FR-6, FR-7, FR-8, FR-9.

## 5. Backend Layers

### 5.1 Router layer

Responsibilities:
- Expose HTTP routes for list, create, update, status change, and delete operations.
- Parse incoming JSON requests into Pydantic models.
- Validate HTTP-level inputs and delegate to the service layer.
- Convert service outcomes to HTTP responses.
- Handle status code mapping for success, validation failure, and not-found cases.

May not do:
- It may not contain business rules.
- It may not directly mutate or inspect the persistence store.
- It may not implement todo lifecycle logic beyond request/response handling.

Traceability: FR-1, FR-2, FR-5, FR-6, FR-7, FR-8.

### 5.2 Service layer

Responsibilities:
- Implement all business logic for creating, updating, deleting, and toggling todos.
- Enforce required title validation and default completion behavior.
- Maintain the invariant that each todo has a unique `Id`.
- Ensure `DateCreated` is assigned automatically on create and cannot be changed by the client.
- Delegate persistence operations to the repository layer.

May not do:
- It may not directly manipulate the Python list in storage.
- It may not handle HTTP request parsing or HTTP response generation.
- It may not depend on frontend-specific code.

Traceability: FR-1, FR-2, FR-3, FR-4, FR-6, FR-7, FR-8, FR-9, FR-10.

### 5.3 Repository layer

Responsibilities:
- Own the in-memory storage for Version 1 as a Python list.
- Provide methods to list all todos, get by ID, add a todo, update a todo, toggle completion, and delete a todo.
- Generate todo IDs and keep the collection in memory while the application process is running.
- Ensure the data storage abstraction is isolated from HTTP and service logic.

May not do:
- It may not contain business validation rules such as checking whether a title is empty.
- It may not process HTTP or API-level concerns.
- It may not be used directly by the frontend.

Traceability: FR-1, FR-5, FR-8, FR-9, FR-10.

## 6. Frontend Components

The frontend uses React functional components and state managed with `useState`. The frontend communicates with the backend through a dedicated API module and renders the todo list in a simple, single-user interface. No authentication flow is required.

| Component | Responsibility | State it owns | Traceability |
| --- | --- | --- | --- |
| `App` | Root component that loads the todo list from the backend, renders the overall layout, and coordinates create, edit, toggle, and delete actions. | `todos` array and top-level UI state that reflects the complete list. | FR-5, FR-6, FR-7, FR-8 |
| `TodoForm` | Provides the form for creating a new todo, with fields for title and description. | Local form values for `title` and `description`, plus validation display. | FR-1, FR-2, FR-4 |
| `TodoList` | Displays all todos in a single list and passes item-level actions to each todo row. | No persistent state beyond list rendering props passed from `App`. | FR-5 |
| `TodoItem` | Renders one todo and supports inline editing, completion toggling, and deletion. | Local editing state when the user edits a todo title or description; also local completion display state if needed. | FR-6, FR-7, FR-8 |

### 6.1 UI behavior requirements

- The main list displays both active and completed todos in one list.
- Completed items are visually distinguishable from active items.
- The user can create a new todo through the form without any account setup.
- The user can update the title and description of an existing item.
- The user can toggle completion status between incomplete and complete.
- The user can remove one or more tasks from the list.

Traceability: FR-5, FR-6, FR-7, FR-8.

## 7. Version 2 Migration Note - exactly which files change when SQLite is introduced

Version 2 introduces SQLite persistence with SQLAlchemy and Alembic. Per the architecture decision, this is a repository-layer change only. The service and router interfaces remain functionally the same; the frontend does not change. The exact application files that change are:

- `backend/app/repositories/todo_repository.py` — replace the in-memory Python list with a SQLAlchemy-backed repository implementation.
- `backend/app/repositories/__init__.py` — update repository exports to reflect the new persistence implementation.

Additional Version 2 framework files are introduced for database support, but they are not part of the existing application logic surface. Specifically:

- `backend/app/db/` or equivalent database setup files for SQLAlchemy engine/session configuration.
- Alembic migration files under `backend/alembic/` for schema evolution.

No router files, service files, or frontend files change in Version 2 because the repository layer remains the only storage abstraction and the external API contract remains stable.

Traceability: FR-10.
